# 스키마와 화면 구현 판단

화면이 백엔드 계약과 문서를 어떻게 읽고 어디서 선을 그었는지 적는다. 기준은 백엔드 코드(`backend/app/schemas/*`, `backend/app/routers/*`)다.

## 백엔드 코드가 기준인 항목

| 위치 | 목업·문서 | 실제 코드 / 구현 |
| --- | --- | --- |
| PRD 7절·SDD 5.13 화면 설명 | 일부 status만 설명 | `ok / partial / insufficient / failed / unsupported` 모두 분기. status와 verdict를 별개로 처리 |
| 목업 README·선박 카드 | position.lon, navstat | `lng`, `navistat` 사용 |
| 목업 README·ETA | sources[], adopted, priority_note | 실제 `ais_eta / mof_eta / calc_eta / trusted_eta / distance_nm`. 채택 사유는 `conflicts[].why`가 있을 때만 표시 |
| 목업 통관 필드 | customs.stage | 실제 `stage_name`, `stage_code`, `plain_explanation`, `next_stage`, `needs_broker`, `history`. 처리 이력 원문은 화면 전용 `customs_detail` |
| 목업 판정 주체 | rule + llm | `decided_by`는 `rule / llm / null`. 합성 enum을 만들지 않음 |
| 목업 실패 | partial이면 watch, 캐시·재시도·로그 | 라우터는 partial에 null verdict를 반환할 수 있음. 재시도 횟수·이벤트 로그 필드 없음. 임의로 만들지 않음 |
| 실패 화면 버튼 | 해수부 기록만으로 판정 보기 | 요청에 이런 모드 필드가 없음. **해수부 근거만 보기**라는 로컬 필터로 구현. 재판정이라고 표시하지 않음 |
| 목업 설정 | 저장 버튼, 모델 변경 | 판단 기준(rules.md 값)은 읽기 전용. 바꿀 수 있는 것은 화면 색(이 브라우저에만 저장)과 카카오톡 연결뿐. 모델 설정 화면은 없음 |
| 목업 조회 이력 | 배열, 선박·MMSI·여유일·재시도·링크·응답 재현 | 실제 `{items, available}`. HistoryItem에는 위 상세 필드가 없음. 실제 필드만 표에 표시 |
| 이력에서 과거 판정 열기 | 행에서 과거 판정 열기 | GET /api/history는 전체 응답을 안 돌려줌. 체험 모드만 fixture trace/request ID에 대응하는 **별도 로컬 스냅샷**을 재생. 실제 모드는 "같은 B/L로 다시 조회" 안내. 새 POST를 과거 결과라고 위장하지 않음 |

## 모르는 값과 빈 값

- `AgentResponse.vessel`은 확정된 배가 있을 때 라우터가 채운다(`_vessel_info`). 없으면 null이고 화면은 null을 정상 처리한다.
- IMO·호출부호·항차·장치장을 추측하지 않아 해당 예시 필드는 null입니다. 후보에도 확인하지 못한 IMO는 null입니다. 통관 이력의 코드가 없으면 빈 문자열입니다.
- `position`에는 AIS 목적지 필드가 없습니다. 목적지는 후보의 `dest`에 있을 때만 표시합니다. `freshness` unknown은 정상 수신으로 표현하지 않습니다.
- 트레이스 ID는 표시하지만 Langfuse 화면 링크는 만들지 않습니다. 동작하지 않는 링크를 두지 않기 위해서입니다.
- 평가 지표는 실제 모드에서 `GET /api/metrics`(운영자 전용)가 `evals/results/`를 읽어 준다. 체험 모드의 `metrics.json`은 **프론트 표시용 자리 채움**이라 점수, 게이트 통과 여부, 평가셋 개수, 갱신일은 null, 실험 이력은 빈 배열이다.
- 서버 환경변수·API 키는 화면 코드가 알지 못한다. 모델명·토큰 상한 같은 서버 설정은 화면에 지어내지 않는다.

## fixture 체험 모드의 경계

- 모든 B/L·선박·좌표·시각은 가공값입니다. `990…` MMSI는 시연용이며 실제 선박과 매칭하지 않습니다. 체험 모드에서는 API·LLM을 부르지 않습니다(지도 바탕 타일만 예외).
- 고정된 예시 B/L은 **그 예시에 저장된 판매 예정일과 M/H 구분**으로만 조회합니다. 날짜·구분을 바꿔도 가공 판정을 재계산하지 않습니다. 다른 조건을 넣으면 안내 오류가 나며, 화면에는 이전 결과임을 표시합니다.
- 실제 모드와 체험 모드는 `lib/api.ts` 안에서만 갈린다. 화면 컴포넌트는 어느 모드인지 몰라도 된다.
- 되묻기는 첫 후보 선택, 또는 후보를 선택하지 않고 항차·ETA 입력 시 저장된 정상 결과로 이어지는 시뮬레이션입니다. 두 번째 후보는 확정되지 않습니다. 실제 식별 알고리즘이 아닙니다.
- 후속 질문은 session/B/L과 질문을 함수에 전달하지만 답변 생성은 하지 않습니다. 저장된 답변을 재생한다는 문구와 반환 근거를 함께 표시합니다.
- 체험 모드에는 서버 진행 소식이 없다. 기다림과 경과 시간만 보이고 단계를 지어내지 않는다.
- 지도는 Leaflet 위에 MapLibre 벡터 바탕(OpenFreeMap)을 얹고, WebGL이 없거나 실패하면 미리 구운 타일(`public/basemap/`), 그것도 없으면 번들 Natural Earth 해안선으로 그린다. 부산항 좌표는 rules.md의 `busan_ref` 값을 demo fixture에 저장했다. 점선은 목적항 방향 안내이며 실측 항적·항로 예측이 아니다.
- 설정의 판단 기준 수치는 `skills/*/rules.md`의 읽기 전용 스냅샷입니다. 화면에서 수정하거나 저장하지 않습니다.
- 데모 둘러보기(`lib/tour.ts`)는 체험 모드 위에서 배 이동과 판정 변동을 가상으로 만든다. 실제 자료처럼 보일 수 있는 부산항 입항 추세 카드는 체험 모드·데모 둘러보기에서 보여 주지 않는다.

## 화면 구성 판단 (AI 입력 중심)

기능·계약은 그대로 두고 배치를 채팅 입력 중심으로 바꾸면서 정한 것들이다.

- **대기 표시**: 타이머로 "이해 → 조회 → 정리" 단계를 넘기지 않는다. 실제 진행과 무관하기 때문이다. 서버가 실제 단계에 들어갈 때 보내는 SSE 소식(POST /api/chat/stream)만 표시한다. Spec: `docs/specs/chat-progress.md`
- 정해진 칸 조회(POST /api/agent: 되묻기 답, 다시 조회)와 체험 모드는 단계 소식이 없다. 기다림과 경과 시간만 보인다
- 새 통로가 없는 서버(404·405)나 응답 전 연결 실패면 POST /api/chat으로 한 번 대신 보낸다. 소식을 받은 뒤 끊기면 다시 보내지 않는다(유료 호출 중복 방지)
- **예시 문장**은 입력창에 채우기만 한다. 실제 모드에서 의도치 않은 유료 호출을 막기 위해서다. 데모 둘러보기에서는 입력칸을 막고 예시를 누르면 미리 만든 답을 바로 보인다
- **선박 자세히 보기**는 선박 표에서 고른 줄 바로 아래에 펼친다(해수부 일정, AIS 위치, 부산까지 거리). 지도는 표 위의 큰 지도가 고른 배로 이동한다
- **서류 사진·PDF**는 채팅 입력창에 첨부해서 보낸다. 서버가 B/L 번호를 확실히 읽었을 때(`bl_status=ok`)만 그 B/L로 채팅 조회를 이어 보내고, 아니면 조회하지 않고 직접 입력이나 다른 사진을 부탁한다. 읽은 값은 다시 보여 주지 않고 중요한 칸 이름만 말한다. 별도 확인 화면은 없다 (docs/specs/document-extract.md)
- **지원 범위 밖** 결과에는 "질문 고치기" 버튼을 두어 입력창으로 돌려보낸다
- **여유 일수 음수**는 "N일 늦음"으로 쓰고 "판매일이 이미 지났다는 뜻은 아닙니다"를 붙인다
- 이력에서 저장된 판정을 열면 선박 표 대신 화물 보기로 바꾼다. 선박 표가 남아 재생 결과를 가리지 않게 한다
- 결과를 다시 받는 동안 지난 결과에 "이전 조회 결과입니다 · 새 결과를 기다리는 중"을 붙인다
- `TopBar.tsx`, `AskPanel.tsx`는 어디서도 쓰지 않지만 파일은 남아 있다

### 자동 검사 범위

- `npm run typecheck`, `npm run test:contracts`(SSE 해석, 백엔드·화면 단계 이름 일치 포함), `npm run build`
- `npm run test:e2e`: 체험 7상태와 페이지별 1440/375px 화면, 1024/768/390px 가로 넘침, 입력 키·한글 조합·500자·중복 전송, 드로어 포커스·inert·Esc·복귀, 지도 정리, 이력 재생, 움직임 줄이기. 실제 모드는 가공 API(:3199)로 일반 사용자 메뉴, /metrics 직접 접근 차단, SSE 단계 순서, 404 대체, 오류 이벤트와 입력 복구, 이력 available:false. axe WCAG A/AA, 페이지 오류, 허용 밖 외부 요청을 함께 검사
- 백엔드 SSE 통로는 `backend/tests/test_chat_stream.py`가 검사한다

### 자동 검사로 확인하지 않는 것

- 실제 Google 로그인, 계정 정지 화면, 회원 정보 입력 화면(로그인 기능은 Supabase 키가 있어야 켜진다)
- 실제 배포(Railway)를 거친 SSE 전달(중간 프록시가 모아 보내는지). 로컬 가공 API로만 검사한다
- 200% 확대, 스크린리더 실기 낭독, 키보드만으로 전 화면 순회(드로어 안 Tab 순환과 Enter 전송만 자동 검사)
